# 单人限时交付：完成优先

已确认单人工作且时间紧或以完成为首要目标时启用本参考。人数未知或多人时先按 context-and-team.md 了解真实团队；不能仅因限时就假定单人。它调整 methods.md 的优先级与复杂度，不另建一套建模流程。默认优先顺序：真实完成交付 → 正确性与可解释性 → 有证据的质量提升 → 可选创新与装饰。

## 先确认什么算完成

从真实题目和交付规范列出必需内容：各项问题的回答、必要模型与实际结果、相称验证、完整可读报告、实际要求的附件／格式／披露。确实缺数据或不可识别时说明限制与能成立的条件答案；不能用空章节、假数字或泛泛套话冒充完成。规范不允许替代的内容缺失，仍记录为未完成。

若用户给出三天，三天只是该任务的规划窗口，不视为某赛事官方时限。未得到实际开始时间、截止时间与可用工作时段前，只做相对预算，不启动倒计时，不声称正在监控。72 小时历时不等于 72 小时可投入工作；实际计划据用户可用时间与题目难度调整。

## 协调职责与用户负担

Praxis 负责维护优先级、依赖、当前可用成果、下一步及简化路线，并自行选择已授权的技术细节。用户负责关键目标、真实偏好、必要输入及真实人工核验。用户不用分别调度七种能力，也不用学习全部算法后才能推进。

在已有 planning/tasks.md 的总览维护单一工作板；项目 README 仍是重要决定入口，不再创建第二套进度表。每个任务记录：必须／改善／可选、依赖、最低完成标准、当前版本、预计剩余投入与置信程度、时间预算、简化路线和下一步。估时不确定就明确范围。

默认只给用户一个当前需要处理的事项。问题可由助手完成就完成；缺失输入才问，批量工作在内部组织。串联分析、实现、验证与写作的上下文由助手维护。每次进度更新简短说明已形成的交付物、主要阻碍和下一项行动，不堆出长待办让用户自行协调。用户重新安排范围时同步工作板。

## 优先级与并行程度

- 必须：原始要求、阻碍有效结果的错误、真实证据、可读交付及明确规范。
- 改善：已完成必需内容后，能改善实际答案的模型比较、稳健性或表达。
- 可选：额外算法、扩展问题、装饰、无实际缺口的依赖与重构。

默认一条主要工作线；长计算期间可做不依赖其结果的来源或文字工作。其他能力按需调用，不能同时向用户抛多个工作方向。优先解除会阻塞多个必需交付的依赖，再处理剩余必需项；改善不能挤掉必需项。

## 滚动形成完整版本

先建报告结构与任务映射。每形成一个有效结果，就同步对应文字、图表和证据位置；不等全部模型完成再开始写。占位只是早期草稿状态，不能算已完成。尽早形成一份覆盖必需任务的可读完整稿，再增量改进。

以下是 72 小时窗口的起始参考，不是已验证的最优安排或官方要求：

| 相对窗口 | 目标 | 调整依据 |
|---|---|---|
| 0–6 小时 | 理清必需交付、依赖与最低路线，建立报告骨架 | 题目与数据明确后缩短背景搜集 |
| 6–24 小时 | 各必需问题形成基线或明确条件答案，结果逐项写入稿件 | 若阻塞，优先简化而非扩充工具 |
| 24–48 小时 | 形成完整可读稿与核心独立核验，显式列出缺口 | 必需未完成时暂停可选探索 |
| 48–60 小时 | 修复关键错误，做能改善答案的有限改进 | 每项改进估计实现、验证及改稿总成本 |
| 60–72 小时 | 检查一致性、格式、导出与交付，保留异常处理余量 | 默认停止可选新模型与工具链迁移，关键错误仍处理 |

预留末段交付余量，不能把全部窗口分给计算。任务或实际可用时间不同，保留上述里程碑逻辑并调整比例，不硬套时点。实际进度明显落后就缩小可选范围，不能靠没有依据的乐观估时掩盖。

## 时间预算与简化路线

探索或调试前说明：它影响哪项任务、预计投入、要看到什么证据才继续，以及超预算采用什么路线。发现明确根因就修复；长期无进展时停止相同尝试，改用可完成的基线、较小范围或条件结论。时间预算不会使错误答案自动合格。

添加模型前估计实现、独立验证、图表与改稿的总成本；只有预期收益与剩余时间支持时才做。搜索限制在能改变当前选择的未知。最后阶段优先保护最新有效的完整稿；可选实验在新运行中进行，不覆盖已核验成果。输入／代码变化后重算真正依赖的结果并同步报告。

## 验收与结束

对照原始要求核查覆盖与真实性，运行 status／evidence 核对数值，检查报告与图表、来源、实际格式及最终文件。保留已通过检查的版本与未解决事项，不以获奖预测替代完成标准。公开或提交仍遵守既有授权要求。

本参考是单人协作策略，不是后台监控、自动排程或已证明能在三天完成任何题目的系统；实际结果需用限时演练验证。
