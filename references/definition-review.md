# 定义、模型和结论的对应检查

分析题目或整合多个子任务时读此文件。目的不是增加固定审批流程，而是发现会改变答案的误读。只检查本题实际存在的风险。

## 先把要求写到能区分对错

对每个问题注明对象、输出、单位与分母、可用信息时点、硬约束、比较范围，以及什么证据能回答它。遇到多个合理解释，先构造一个能让两种解释得到不同结果的小例子；仍无法确定且会改变主要结论时才询问用户。不能用算法替题目定义目标。

- “平均增长”：平均各期增长率，与首尾的复合增长率是两种量。用先增长 100% 再下降 50% 的例子区分：算术平均为 25%，复合增长为 0%。根据题意确定分母与时间跨度。
- “所有点都有设备覆盖”：每点可由不同设备负责；“存在一个设备覆盖所有点”更强。不要因对称例子给出相同答案就混为一谈。
- “面积覆盖率”：两区域有重叠时，覆盖面积使用并集；除非任务定义的是重复服务次数，否则不能简单相加。
- “最优”：说明是已检查候选中最好、离散网格中最好、局部解还是全局最优。有限采样不能直接支持连续空间的全局断言。
- 预测：每个开发和最终测试样本的目标时间必须分开；特征与处理参数只能使用当时可获得的信息。

## 用最有区分度的检查

先检查会改变答案的命题，优先选择不同推导、手算、不变量、小规模穷举、上下界或独立基准。选择检查是为了验证具体结论，不是凑数量。复用同一个目标函数再算一次只能检查运行一致性；同一套错误定义也会得到一致结果。

发现失败后修复根因与直接依赖，补上针对性回归。检查已通过且没有新的矛盾就继续交付，不反复进行同样审计；若关键问题尚未解决，不能因达到预设轮次就宣布通过。

## 跨任务整合

复用上游结果时明确运行版本、同名变量含义、单位、参数和舍入规则。上游发生变化，重算真正依赖它的结果。情景假设不能在后续章节变成已证实事实；候选集合最优不能在摘要里变成全局最优。当前运行器记录单个案例的证据，不自动管理多个案例的依赖图；跨案例依赖需要在 planning/tasks.md 明确记录并核查。

报告前使用 references/automation.md 的证据索引，把记录的数值任务连接到结果字段与独立检查。未写入清单的任务不会被工具发现；正文图表、论证和格式要求仍需逐项人工对照。
