# 数据版本如何改变补货决策

**简体中文** · [English](README.en.md) · [案例总览](../README.md)

一家合成门店每天08:00为两种商品补货，总容量40单位。当天需求的预测后来会被修订；如果用最终快照重建早上的订单，未来信息就会进入过去。这份原创案例把版本选择、受限分配、实际代价和未决项接成一个完整任务。

[完整分析](report.md) · [逐日结果](results.json) · [独立核验](checks.json) · [题目与固定输入](data/problem.md)

| 同一组8天、16个目标 | 预测MAE（单位） | 事后成本（声明成本单位） | 缺货／过量（单位） | 截点时是否可用 |
|---|---:|---:|---:|---|
| 当时声明可用的预测 | 5.4375 | 248 | 46／34 | 是，条件限于合成账本 |
| 固定20／20基线 | 3.9375 | 157 | 24／39 | 是 |
| 无效的事后最终快照 | 0 | 36 | 9／0 | 否 |

固定基线在这里优于当时可用的预测。最终快照的零误差揭示了信息泄漏造成的成绩膨胀，不能成为采用该预测的理由。容量仍然约束订单，所以即使事后知道需求，也有9单位缺货。

## 未决项也是结果

原名单有20个查询、10个决策日。17个查询找到唯一可用版本；另外三个分别缺发布时间、最新发布同刻冲突、截点前尚未发布。两天的自动订单保持未决，实际结果保留这些行，没有缩小分母。第9天需补齐A的发布记录并裁定B的冲突；第10天需找到A在截点前可用的预测。运营备用策略尚未建模。

`asof_join` 复用Pandas按键和截点选择版本；未来事件只要提前公布仍可使用。订单以HiGHS整数规划最小化预设缺货／过量损失。另一份验证器逐版本扫描UTC时间，并枚举每一天全部861组可行整数订单。改变17个截点后版本的数值，已支持的映射与订单保持不变。

## 计算复现

在源码或导出包的核心目录，以尚不存在的路径运行：

```bash
uv run --locked python demos/data-vintages/run.py --output /path/to/new-vintage-case
```

生成原件只读副本、模型与独立验证器、运行及依赖快照、JSON结果、完整英文分析、检查和四项任务的证据索引。已有目录拒绝覆盖。只有一份精选成品；重放写到新的用户目录。

时间戳及损失均为事前声明的合成设定。这验证了信息边界和计算，没有验证真实发布来源、完整历史账本、预测不确定性、商业收益或美赛奖档。专业职责见[数据分析](../../references/data-analysis.md#按决策时刻选择数据版本)；产物身份见[demo.json](demo.json)。
